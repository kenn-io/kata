# Kata 0.14.1 Docs and Web Screenshots Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finalize the Zensical docs for the shipped Kata 0.14.1 release and publish reproducible Web UI screenshots generated from disposable synthetic data.

**Architecture:** Reuse `web/tests/fixtures.ts` to run the production embedded browser application against temporary local and configured-remote daemons. A single screenshot orchestrator generates the existing TUI SVGs plus four new Web UI PNGs, validates one shared asset contract, and feeds both local preview and a single-commit orphan `docs-assets` branch; the docs hydrator extracts only that validated contract at build time.

**Tech Stack:** Bash, Go behavior tests, Playwright/TypeScript, Kata's public browser API, Git orphan branches, Zensical.

## Global Constraints

- Document the shipped `v0.14.1` behavior by checking the tagged source and public release notes.
- Keep all generated PNG/SVG assets off the working branch and under the one-commit orphan `docs-assets` branch.
- Use only neutral synthetic names such as `example-project`, `example-inbox`, `user-a`, and `example-remote`.
- Run every daemon, database, workspace, browser, and binary from the existing isolated Playwright fixture or another temporary directory.
- Do not change persisted database schema or migrations.
- Test publisher and hydrator behavior in temporary Git repositories; do not add Bash content-assertion tests.
- Force-push `origin/docs-assets` only after source changes are committed and all generated assets pass the private-data scrub.
