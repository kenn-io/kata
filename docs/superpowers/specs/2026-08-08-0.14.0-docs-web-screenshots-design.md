# Kata 0.14.0 Docs and Web Screenshots Design

## Goal

Finalize the public Zensical documentation for Kata 0.14.0 against the shipped
code and add reproducible Web UI screenshots generated from disposable,
synthetic issue data. Generated screenshots remain outside `main` on the
single-commit orphan `docs-assets` branch and are hydrated into the docs tree at
build time.

## Scope

The documentation pass covers every 0.14.0 changelog item:

- the Web UI, including projects, issue collections, issue editing,
  relationships, recurrences, and configured daemon switching;
- the native project-bound MCP server;
- cross-project `list` filters and scoped label filters for `search`;
- direct issue-ref opening in the TUI;
- daemon profiling endpoints;
- Markdown rendering in `show`;
- scoped filters composed with `ready --all` and `next --all`;
- parked-issue exclusion from ready queues;
- Git-root-bounded workspace configuration discovery;
- bounded federation ingest work and synchronization timeouts;
- installer compatibility with releases that predate embedded Web UI assets;
- CLI/daemon version mismatch detection during list operations.

The pass will finalize the 0.14.0 changelog entry, correct inaccurate or
incomplete existing descriptions, and add a focused Web UI guide to the public
navigation. It will not redesign the application, change its persisted schema,
or broaden the release beyond shipped 0.14.0 behavior.

## Documentation Structure

Add `docs/guide/web-ui.md` as the task-oriented entry point for browser users.
It will explain how to launch the UI, how the sidebar and collections map to
projects and issue state, how issue detail manages fields and collaboration,
how relationship graphs and recurrences work, and how the daemon switcher uses
server-side configured credentials. Existing reference pages remain the source
for detailed CLI, configuration, HTTP, authentication, and deployment
contracts.

The overview will show the Web UI alongside the TUI and link directly to the
new guide. The Zensical navigation will place the guide with other user-facing
guides. The changelog will move shipped MCP content out of `Unreleased`, add a
dated 0.14.0 section based on the tagged changelog, and retain only genuinely
unreleased work above it.

## Screenshot Architecture

Reuse the real production-browser Playwright fixture in `web/tests/fixtures.ts`.
That fixture already builds the embedded Web UI, launches branch binaries
against temporary homes, workspaces, databases, and loopback ports, creates a
local and configured remote daemon, and establishes a genuine browser session.
The docs capture therefore exercises the same daemon, embedded assets, session
exchange, API, and Svelte application shipped in the release.

A dedicated Playwright spec will seed neutral synthetic projects, issues,
links, checklist items, comments, labels, owners, priorities, and recurrence
rules through Kata's public API. It will use a fixed desktop viewport, dark
color scheme, disabled animations, hidden carets, and explicit readiness
assertions before writing each PNG. The captures will be:

- `web-ui/workspace.png`: project navigation, collections, filters, and a
  representative issue hierarchy;
- `web-ui/issue-detail.png`: Markdown description, properties, comments,
  checklist, links, and recurrence information;
- `web-ui/relationships.png`: the reachable issue graph;
- `web-ui/daemon-switcher.png`: the configured local and remote daemon menu.

Synthetic names will use stable neutral examples such as `example-workspace`,
`example-inbox`, `user-a`, and `daemon.example`. No local project, account,
host, or customer data will enter the fixture or images.

## Generation and Publication Flow

Add one aggregate screenshot command that clears a staging directory, runs the
existing federation TUI generator and the new Web UI generator into that
directory, validates the exact expected asset set, and writes the branch
README and machine-readable manifest. `make docs-screenshots` and the branch
publisher will both call this aggregate command so local preview and published
assets cannot drift.

The publisher will follow the established generated-assets pattern: validate
the configured branch name, generate or accept an explicit source directory,
reject missing, unexpected, or symlinked assets, create a fresh temporary Git
repository, commit only the validated asset set, and atomically update the
local `docs-assets` ref. `--push` will force-push that single orphan commit to
`origin/docs-assets`, as explicitly approved for this task.

The hydrator will require every TUI and Web UI asset. It will continue to use a
local branch when available, otherwise fetch the remote orphan branch, extract
it under the ignored `docs/assets/screenshots/` directory, and fail clearly
when the branch or any required asset is unavailable. Vercel and local strict
docs builds will continue through the same hydration path.

## Failure Handling

Capture commands fail if required toolchains are absent, a daemon exits, a
browser state does not become visible, or an expected screenshot is empty.
All daemons, temporary homes, databases, ports, binaries, and browser state are
owned by the existing isolated fixture and removed on exit.

Publication fails before moving the branch ref when the source contains a
missing, extra, or symlinked asset. The temporary repository prevents partial
updates to the existing orphan branch. Hydration replaces the ignored target
only from a validated branch and reports which expected contract failed.

## Testing and Verification

Behavior-based tests will exercise publisher and hydration outcomes in
temporary repositories rather than asserting script contents. The Playwright
capture spec will assert the seeded data and each target UI state before
capturing. The implementation will follow red-green-refactor for new script
behavior.

Final verification will include the focused generated-assets tests, the real
Web UI capture, exact asset validation, Web UI checks relevant to the capture
fixture, `scripts/check-docs.sh`, and a strict Zensical build. Generated images,
the source diff, commit messages, and the orphan branch contents will be scanned
for private data before publication.

## Delivery

Commit the source documentation, tests, and generators on the working branch
without rewriting history. After that commit passes verification, regenerate
the assets from the committed source, update the one-commit orphan
`docs-assets` branch, and force-push that branch. The generated images are not
committed to the working branch.
